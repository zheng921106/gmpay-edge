# GMPay Edge 支付测试中心设计

**状态：** 已确认，等待实施计划

**日期：** 2026-09-01

**英文配套：** `2026-09-01-payment-test-center-design.md`

## 目标

新增一个感知商户环境的支付测试中心，让商户在后台内完成 GMPay 或 EPay
支付的发起、支付、回调和诊断。一次测试必须覆盖请求签名、商户 API 鉴权、
订单创建、收银台、支付入账、订单状态、Webhook 投递、回调应答和最终通过/失败证据。

测试中心属于现有多商户产品，不新增第二套订单服务、支付状态机、Webhook 实现、
路由、身份认证或数据访问层。

## 现状与缺口

系统已有商户范围的沙盒/正式环境、环境级 API Key 和收款方式、GMPay/EPay
共享订单创建、收银台、支付入账、Webhook Outbox 投递、重试记录和商户订单列表。

现有开发工具不能形成正式产品闭环：

- 开发订单创建和任意状态修改仅在本地 `import.meta.env.DEV` 构建中开放；
- 模拟付款面向平台管理员，而且只检查 `mock` 适配器，没有完整校验商户和环境边界；
- 请求、订单、付款和回调证据散落在不同页面；
- 内置支付目录以主网为主，没有把测试网表示为独立网络身份。

## 已确认决策

- 建立统一支付测试中心，不创建独立沙盒子系统。
- 同时提供“引导测试”和“API 调试台”。
- 同时支持 GMPay 和 EPay，默认 GMPay。
- 沙盒同时支持内置模拟器和显式配置的真实测试网。
- 正式环境在二次确认后可以发起真实订单，但永不显示或接受模拟操作。
- 同时支持系统内置回调接收器和商户自定义回调 URL。
- 每个新商户自动获得可立即测试的沙盒凭据、模拟收款方式、内置回调能力和示例预设。
- 真实测试网分级启用。首期覆盖 TRON Nile、Ethereum Sepolia、Base Sepolia、
  BSC Testnet 和 Polygon Amoy。TON、Aptos、Solana 在真实测试网适配器和目录完成
  并验证前仅支持模拟器。
- 真实测试网和正式主网的收款地址由商户自行提供。GMPay Edge 不创建或保存私钥、助记词。

## 产品结构

在现有“开放与集成”导航组增加 `/admin/test-center`“支付测试中心”。路由保持轻量，
挂载 `src/features/payment-testing` 内归属明确的功能页面。

页面始终跟随当前商户/环境上下文，提供三个语义视图：

1. **引导测试：** 收集协议、模式、API Key、金额、币种、资产、网络、返回 URL 和
   回调方式，然后驱动一次完整运行。
2. **API 调试台：** 提供结构化参数和原始请求视图，在服务端签名，通过真实协议处理器发送，
   展示脱敏请求与响应。
3. **测试记录：** 列出已持久化的测试运行，并打开包含统一时间线的运行详情。

现有商户/环境切换器继续作为唯一权威。所有查询键、加载器、修改、URL 和服务函数都解析
当前上下文；切换上下文后使测试中心数据失效并重新加载。

## 环境能力矩阵

| 能力 | 沙盒 | 正式环境 |
| --- | --- | --- |
| 内置支付模拟 | 允许 | 服务端拒绝 |
| 真实测试网支付 | 允许 | 服务端拒绝 |
| 真实主网支付 | 服务端拒绝 | 允许 |
| 后台发起订单 | 允许 | 二次确认后允许 |
| 内置回调接收器 | 允许 | 允许 |
| 商户自定义回调 | 允许 | 允许 |
| API Key、地址、测试和订单 | 仅沙盒范围 | 仅正式范围 |

界面同时使用文字、图标和语义色表示环境，不能只依赖颜色。正式操作确认框必须显示商户、
金额、币种、资产、网络、回调目标和“真实资金”字样。

## 完整测试运行

一个 `payment_test_run` 是一次订单尝试的聚合根：

```text
选择商户和环境
  -> 选择 GMPay/EPay 与支付模式
  -> 执行就绪检查
  -> 在服务端构建并签名协议请求
  -> 调用现有商户 API 的 Request/Response 处理器
  -> 创建范围化订单和收银台 URL
  -> 模拟提供商事件或等待真实网络付款
  -> 进入现有支付状态机
  -> 提交现有 Webhook Outbox 事件
  -> 投递到内置或自定义回调端点
  -> 汇总证据并标记通过或失败
```

测试中心服务端构造真实 `Request`，调用公开路由所使用的同一个 GMPay/EPay 处理器，
不能直接调用 `createOrder`。这样无需不可靠的 Worker 自请求，也能覆盖解析、签名验证、
API Key 范围、限流、幂等、收款方式分配和协议响应格式。

## 引导测试

引导流程在创建订单前执行预检：

- API Key 已启用、未过期、属于当前环境并拥有所需订单权限；
- 收款方式属于当前商户/环境且已经就绪；
- 资产、网络、金额限制、汇率、连接健康和 Queue 绑定可用；
- 自定义回调 URL 通过现有 HTTPS、DNS、SSRF 和重试策略检查；
- 模拟器、测试网、主网模式与当前环境及支付网络类别一致。

创建成功后展示协议响应和打开收银台操作。测试运行通过仅在页面可见、网络在线时轮询，
同时接受 Queue 驱动的状态变化。刷新或重新登录后可以继续追踪同一次运行。

## API 调试台

API 调试台使用 GMPay/EPay 分段控件，并提供同一类型化请求的结构化表单和原始视图。
页面展示：

- 根据环境解析的 API 地址和 HTTP 方法；
- PID、参与签名的字段、规范化签名原文和最终签名；
- 脱敏后的请求头和请求体；
- 响应状态、响应头、响应体、请求 ID 和耗时；
- 创建成功后的订单查询和打开收银台操作。

API Secret 只在服务端单次请求生命周期内解密，永不返回客户端，不保存到测试运行快照，
不写入 KV 或日志。原始模式在签名前使用现有协议 Zod Schema 解析和验证。

## 正式环境二次确认

正式环境预检先创建一个 `ready` 测试运行，并返回短期有效的签名确认令牌，绑定：

- 测试运行、用户、商户和正式环境 ID；
- 协议和 API Key ID；
- 金额、币种、资产、网络及回调目标摘要；
- 过期时间和随机 Nonce。

原始令牌不入库；测试运行只保存 Nonce 哈希和过期时间。确认时先原子消费 Nonce，
再调用协议处理器。任何绑定字段变化、重复使用、换账号或超时都必须拒绝。
该确认机制独立于正常订单幂等键，不能削弱订单幂等约束。

## 沙盒模拟器

模拟器是测试专用“提供商事件源”，不是订单状态编辑器。每个场景生成类型化、类似真实提供商
的付款事件，并进入正常归因、支付入账、确认、状态迁移、审计和 Webhook Outbox 链路。

首批场景包括：

- 精确金额成功付款；
- 部分付款后补足；
- 超额付款；
- 确认数递增；
- 提供商交易失败；
- 重复事件投递；
- 订单过期后的迟到付款；
- 模拟链重组导致确认回退并恢复；
- 回调失败后进入正常重试流程。

现有直接写任意订单状态的开发函数不能被线上测试中心复用。待场景引擎具备等价测试后，
该函数继续仅限本地或删除。

每次模拟调用都必须同时满足：

```text
当前环境是 sandbox
测试、订单、API Key、收款方式属于同一商户和环境
测试模式是 simulator
订单收款快照适配器是 mock
操作者拥有商户 update 权限
场景迁移符合当前持久化状态
```

## 真实测试网模型

测试网是一级支付网络，不能作为隐藏在主网后的备用 URL。扩展全局支付链路目录，增加明确的
网络类别：`mainnet`、`testnet` 或 `simulated`。新增独立网络和资产记录：

- `tron-nile`；
- `ethereum-sepolia`；
- `base-sepolia`；
- `bsc-testnet`；
- `polygon-amoy`；
- 一个全局模拟网络，但只允许沙盒初始化流程使用。

每个测试网拥有独立 RPC/HTTP/WSS 连接、链身份、合约地址目录、精度、确认数、健康状态、
扫描游标和收款方式。合约地址和公共节点只在实施时从官方来源验证后加入，不能编造回退值。

就绪检查强制以下映射：

- 沙盒只接受 `testnet` 或 `simulated` 网络；
- 正式环境只接受 `mainnet` 网络；
- 没有明确测试环境的交易所或钱包适配器不显示为真实测试网选项。

真实测试网收款使用正常适配器和扫描器。某条链支持模拟器不等于该链已具备真实提供商就绪证据。

## 自动沙盒初始化

商户创建事务在现有初始化基础上增加：

- 一个启用的沙盒 API Key，包含 GMPay/EPay 订单创建、读取、更新和资产读取权限；
- 一个模拟网络/资产收款方式；
- 内置回调接收能力；
- 一个可直接运行的示例预设，但商户点击开始前不自动创建订单。

生成的 API Secret 使用现有密钥契约加密，并在引导流程中只展示一次。测试中心后续可以在服务端
使用它生成签名请求，但不能再次向用户展示。只有商户配置有效公共地址后，才启用真实测试网收款方式。

## 数据持久化

在现有支付/Webhook 归属边界内增加以下 Drizzle 表。

### `payment_test_runs`

必要字段包括：

- `id`、`merchant_id`、`environment_id`、`created_by_user_id`；
- `protocol`（`gmpay` 或 `epay`）；
- `payment_mode`（`simulator`、`testnet` 或 `live`）；
- `api_key_id`、`external_order_id` 和可空 `order_id`；
- `callback_mode`（`builtin` 或 `custom`）及脱敏目标快照；
- `status`（`ready`、`running`、`passed`、`failed`、`cancelled` 或 `expired`）；
- 版本化、限长、经过 Schema 验证的脱敏请求/响应快照；
- 正式运行所需确认 Nonce 哈希、过期时间和消费时间；
- 结构化失败码、开始/完成时间及标准时间戳。

测试创建使用范围化唯一幂等约束，订单关联是可空唯一值。测试记录和活动运行查询使用范围列开头的索引。

### `payment_test_callback_receipts`

必要字段包括测试运行、Webhook 事件/投递/尝试身份、签名状态、限长脱敏请求头和请求体、
响应确认、接收时间及标准时间戳。每次重试显示为独立尝试，相同投递身份保持幂等。

内置回调路由使用每次测试独立的高强度不透明令牌，只保存哈希和过期时间。处理器限制请求体大小，
验证令牌和 Webhook 签名，保存接收记录，返回协议要求的纯文本确认；无效请求不能暴露测试是否存在。

## 时间线与通过标准

测试详情查询组合现有记录，不复制它们的状态：

- 测试运行和脱敏协议请求/响应；
- 订单和付款快照；
- 支付交易与确认变化；
- 关联测试/订单的审计记录；
- Webhook 事件、投递、尝试、响应状态和耗时；
- 选择内置回调时的接收记录。

正常测试只有在订单到达预期成功付款状态，并且必要回调投递成功后才能通过。部分付款、超额付款等
场景拥有明确预期状态，只有状态和 Webhook 证据都出现后才能通过。订单已付款但回调失败时，
按照现有重试策略保持失败或进行中，不能误报通过。

## 权限与导航

复用商户权限位：

- `merchant:read`：列出测试和读取详情；
- `merchant:create`：执行预检并发起订单；
- `merchant:update`：运行沙盒场景、取消活动测试、检查真实付款和重试 Webhook；
- 测试中心不使用删除权限位。

平台 root 仍必须选择具体商户/环境上下文，不能绕过环境模式检查。导航可见性来自共享导航权威，
与服务端权限保持一致。

所有标识符都在服务端重新按范围检查。其他商户/环境的测试或订单 ID 只能返回通用不存在或无权限错误。

## 错误处理与幂等

- 每个服务入口使用 Zod 对输入只验证一次，并在服务函数或 HTTP 边界映射结构化领域错误。
- 预检失败显示可执行的错误类别，但不暴露 SQL、解密凭据、提供商敏感载荷、内部 ID 或堆栈。
- 发起测试使用客户端生成的幂等键，并按商户、环境、协议和 API Key 隔离。
- 协议订单创建继续使用现有商户订单幂等模型。
- 场景事件使用确定性的测试/场景/步骤身份，重试不能创建重复付款。
- 页面刷新、Queue 重投和回调重试都从持久化状态继续。
- 取消测试绝不能取消、退款或修改已经付款的真实订单。

## 界面、主题、无障碍与国际化

复用现有 `PageHeader`、ProForm、ProTable、Radix/shadcn 控件、环境徽标、状态徽标和设计令牌。
不嵌套卡片，不引入第二套向导/表单库。界面保持紧凑、任务导向，不做营销页面。

浅色和深色分别定义语义表面、边框、代码背景、警示状态和时间线颜色。沙盒与正式标签在两种主题中
都保持可读。固定控件使用稳定尺寸，移动端文字换行且不能重叠。

所有用户可见文字加入六种 Paraglide 语言。必须支持键盘操作、可访问名称、焦点恢复、减少动画、
可见错误关联和屏幕阅读器环境播报。

## 可观测性与保留策略

记录不涉及隐私的预检、协议请求、订单创建、支付检测、确认和回调投递耗时。复用现有请求 ID、
D1 行指标、Queue 年龄/重试指标和审计日志。永不记录签名密钥或未脱敏的回调授权值。

测试运行和回调接收记录遵循现有商户保留设置，并增加测试数据最短/最长周期。删除过期测试证据时，
不能删除对应正式订单、付款、Webhook 或审计记录。

## 迁移与双运行时一致性

前向迁移按顺序执行：

1. 增加支付网络类别和已明确支持的测试网/模拟网络目录记录；
2. 创建测试运行、回调接收表和范围列开头的索引；
3. 为现有商户幂等补齐缺失的沙盒初始化资源；
4. 保持所有生产数据、现有网络编码、订单 URL、API 凭据和回调投递不变；
5. 检查重复/孤儿记录和查询计划，然后执行 `PRAGMA optimize`。

Workers/D1 和 Bun/SQLite 使用相同 Schema、服务函数、Queue 行为、调度恢复和回调处理。
测试中心的任何功能都不能依赖 `import.meta.env.DEV`。

## 验证

重点自动化覆盖：

- Schema、迁移幂等、沙盒初始化和查询计划；
- GMPay/EPay 签名测试请求经过各自真实处理器；
- API Secret 脱敏及正式确认令牌重放、篡改、过期攻击；
- 跨商户、跨环境读取/写入/模拟攻击；
- 模拟场景经过支付入账、状态迁移、Outbox、回调接收、重复处理和重组恢复；
- 主网/测试网/模拟网络就绪隔离；
- 自定义回调 SSRF 校验和 Webhook 重试证据；
- 浅色/深色、移动/桌面、键盘、语言和路由选中；
- Workers 与 Bun 运行时适配一致性。

保留的真实提供商冒烟套件继续作为无条件跳过的手工资产。已配置测试网和受控真实资金正式订单
必须提供手工运行证据。

所有本地可执行工作完成后，在同一最终代码树上仅运行一次完整门禁：

```bash
bun run typecheck
bun run test
bun run check
bun run build
bun run build:bun
```

## 验收场景

1. GMPay 沙盒模拟器创建订单，通过真实状态机完成付款，投递到内置回调并标记测试通过。
2. EPay 沙盒模拟器创建订单，测试自定义回调、响应和重试，达到预期最终结果。
3. 首期任一已配置测试网收到真实转账，扫描确认、变更订单、投递回调并通过测试。
4. 正式环境需要有效的一次性确认，创建真实主网订单，并在任何写入前拒绝所有模拟接口。
5. 两个商户的沙盒/正式数据不能互相列出、读取、修改、模拟、确认或重试对方测试、订单、
   API Key、付款和回调。

## 实施阶段

1. 持久化、环境模式不变量、范围授权和迁移。
2. 模拟提供商事件引擎与内置回调接收器。
3. 引导测试、API 调试台、历史、时间线和六语言界面。
