# GMPay Edge 多商户设计

**状态：** 已确认，等待实施计划
**日期：** 2026-09-01

## 目标

将 GMPay Edge 从单商户网关升级为多商户网关，同时保持现有 GMPay/EPay
协议、当前生产订单、Cloudflare Workers/Bun 双运行时和现有平台 RBAC 不变。

系统同时支持平台创建商户和商户自助注册。注册自动通过：每个新商户立即拥有
启用的沙盒和生产环境。一个用户可以加入多个商户，并在不同商户中拥有不同角色。

## 已确认决策

- 使用一个共享 D1/SQLite 数据库，并强制执行行级租户隔离。
- 商户拥有的数据增加商户和环境范围。
- 支付链路/资产等只读能力目录继续作为平台级共享数据。
- 平台权限与商户范围权限分开计算，但继续使用现有 RBAC 原语和权限位掩码。
- 商户 API 从已认证 API Key 推导商户和环境，不信任请求中的商户标识。
- 已登录 UI 使用经过验证、签名的 HttpOnly 上下文 Cookie 保存当前商户/环境。
  当前选择只决定数据范围，不改变用户的平台权限集合。
- 现有数据迁移到一个自动生成的默认商户的生产环境，已有 API Key 和订单 URL 保持有效。

## 租户模型

### 商户和环境

新增 `merchants`，包含 `id`、`slug`、`name`、`status`、`created_by_user_id`
和时间戳。商户状态为 `active` 或 `suspended`。

新增 `merchant_environments`，包含 `id`、`merchant_id`、`code`（`sandbox` 或
`production`）、`status` 和时间戳。通过 `merchant_id + code` 唯一约束保证每个商户
恰好拥有一个沙盒和一个生产环境。环境状态为 `active` 或 `suspended`。

环境记录是规范范围键。商户数据表可以同时保存 `merchant_id` 和 `environment`
以便查询和显式校验；在 SQLite 约束允许时增加指向环境记录的外键。

### 成员和角色

新增 `merchant_memberships`，包含 `merchant_id`、`user_id`、`status`、邀请元数据
和时间戳。唯一约束防止重复成员关系。

扩展现有角色模型，使角色可以是平台范围角色，或绑定到一个商户。商户内角色名在
商户范围内唯一；内置商户所有者角色在仍是最后一个所有者时不能删除或禁用。
现有 `role_permissions` 和 `user_roles` 继续作为权限原语，同时在商户角色计算时
增加成员关系校验。

平台用户继续使用现有全局角色。商户访问权限是当前商户下用户所有启用角色与平台权限
的并集，不存在“当前角色”权限状态。

默认商户角色为 `owner`、`admin`、`operator`、`viewer`。权限位通过现有权限注册表
初始化。所有者可邀请/移除成员并管理商户设置；viewer 只读。

## 商户数据

以下资源增加商户和环境范围：

- API Key 及其加密凭据
- 收款方式及收款方式资产
- 支付入口及入口凭据
- 订单、幂等键和商户订单元数据
- 出站 Webhook 事件、投递、尝试和商户回调状态
- 商户支付设置、费率调整、品牌和运营设置
- 商户 Telegram Bot、通知绑定和商户订单命令

支付链路、支付资产、权限注册表、语言目录和平台运营遥测继续为全局数据。
只能通过订单外键访问的支付子记录可以继承订单范围；但列表查询仍必须通过带范围的订单
进行连接。

所有新增或修改的唯一索引都必须审查是否包含商户/环境范围。例如 API 幂等键、外部订单号、
收款目标和提供商来源标识，都应按商户和环境生效。按范围过滤的查询，索引应以范围列开头。

## 请求与授权上下文

### 商户 API

`authenticateGmpayParameters` 和 `authenticateEpayParameters` 除现有 API Key 主体外，
还返回 `merchantId`、`environmentId` 和环境代码。订单、支付选项、回调和 Webhook 服务
均接收这个不可变上下文。

现有 API 路径和请求/响应格式保持不变。沙盒或生产由 API Key 决定。生产 Key 不能访问沙盒
记录，沙盒 Key 不能创建或查询生产记录。

订单服务的所有商户操作都必须拥有范围上下文。缺少上下文时返回结构化授权错误，不能回退到
全局数据。资源不存在响应不能泄露其他商户或环境是否存在对应资源。

### 已登录后台

新增商户上下文加载器，根据当前用户和成员关系验证签名上下文 Cookie。平台管理员可以选择
任意启用商户；其他用户只能选择自己加入且启用的商户。

新增环境上下文加载器，只允许选择当前商户下启用的环境。上下文变更请求必须使用现有可信
Origin/CSRF 防护，并写入审计日志。

现有后台服务函数必须同时取得平台权限；涉及商户数据时还必须取得已验证的商户上下文。
客户端隐藏不能代替服务端授权。

## 注册和界面

新增 `/sign-up`，使用 Better Auth 凭据注册。注册事务一次性创建用户和商户，创建两个环境，
把注册用户加入为所有者，然后跳转到商户初始化页面。注册不进入审核队列。

新增 `/admin/merchants` 平台商户管理页，支持创建、暂停商户、暂停环境和查看成员关系。
已登录外壳增加商户切换器和沙盒/生产切换器。现有资源页面继续使用语义路由，但读取当前上下文。

API Key 页面显示环境标识，只能为当前环境创建 Key。成员管理只作用于当前商户。平台页面可以
显式选择商户，相关操作写入审计日志。

## 数据迁移

迁移必须向前兼容，并在应用强制要求非空范围前完成：

1. 创建商户、环境和成员关系表。
2. 创建一个默认商户及其沙盒/生产环境。
3. 把现有启用用户绑定为默认商户所有者；已有平台角色按原模型保留。
4. 将现有 API Key、支付配置、订单、Webhook、Telegram 配置和设置归入默认商户生产环境。
5. 为现有表增加范围列并回填全部旧数据。
6. 创建范围索引并替换不安全的全局唯一约束。
7. 在启用新代码路径前校验行数、空值/孤儿记录、范围内重复键和查询计划。

迁移应在迁移运行器支持的范围内保持幂等，不能删除源数据。Cloudflare 远程迁移只能在备份
和证据检查后通过维护的 predeploy 流程执行。Bun 导入/导出继续使用现有清单和校验和验证。

## 错误处理与安全

- 缺少、暂停或格式错误的上下文必须拒绝请求。
- 每个服务入口都检查成员关系和环境状态。
- 跨商户资源访问映射为通用不存在或无权限错误。
- 商户切换、成员变更、环境状态、API Key 生命周期和平台跨商户操作必须审计。
- 限流和幂等在适用时按商户、环境和 API Key 隔离。
- Webhook 回调校验和重试策略保持不变，范围随订单和投递记录保存。
- 解密凭据、会话令牌和 API Secret 不能进入上下文 Cookie、缓存键或日志。

## 验证

重点测试覆盖迁移回填、成员/角色计算、上下文 Cookie 校验、API Key 范围推导、订单与幂等
隔离、Webhook 隔离、沙盒/生产隔离和旧 API 兼容。安全测试通过服务函数和 HTTP 端点尝试
跨商户读写。

E2E 测试覆盖注册、自动创建环境、成员邀请、多商户切换、环境切换、API Key 创建和结账访问。

最终代码树执行：

```text
bun run typecheck
bun run test
bun run check
bun run build
bun run build:bun
```

发布验证包括 D1 远程迁移输出、Cloudflare Worker 版本、GitHub 提交一致性、生产健康检查，
以及沙盒 Key 与生产 Key 不能互相访问的线上验证。

## 实施阶段

1. Schema、迁移、范围类型和上下文基础设施。
2. 成员/商户 RBAC 和注册事务。
3. API Key、订单、支付、Webhook 和 Telegram 的范围传递。
4. 商户/环境选择器和范围化后台页面。
5. 隔离测试、迁移演练、部署和生产冒烟验证。

每个阶段在替换路径具备集成测试和可回滚迁移步骤之前，保持原有应用路径可用。
